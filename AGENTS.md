# Правила работы с библиотекой PMG

## Репозиторий и размещение файлов

- Репозиторий: `magin67/pmg-notes`. Рабочая и публикуемая ветка: `v5`.
- Исходники публичной библиотеки: `pmg-library`; русские заметки: `pmg-library/ru`, английские: `pmg-library/en`.
- Служебные инструкции: этот файл и папка `instructions`, вне `pmg-library`. Они видны в публичном репозитории, но не включаются в текущую сборку сайта.
- Сборка публикации задана в `.github/workflows/deploy.yml`: `npx quartz build -d pmg-library`. Не менять папку источников ради служебных файлов.

## Что прочитать перед работой

1. [Инструкцию по оформлению заметок](instructions/Оформление%20заметок.md).
2. Актуальные файлы спецификации и терминологии:
   - `pmg-library/ru/Основания/Спецификация ядра PMG.md`;
   - `pmg-library/ru/Основания/Терминология PMG.md`.
3. При работе с английским текстом также:
   - `pmg-library/en/Foundations/Core specification.md`;
   - `pmg-library/en/Foundations/PMG terminology.md`.
4. Затрагиваемые заметки, навигацию соответствующей серии и непосредственно связанные материалы.

Читать актуальные версии из репозитория, не подменять их копиями из прежних диалогов. Инструкции пользователя в текущей задаче имеют приоритет. Эти правила не предоставляют дополнительных технических прав доступа.

## Порядок работы

- Обсуждение, вопросы и планирование сами по себе не означают поручения изменять файлы.
- Поручения «пиши заметку», «приступай», «исправь» в рамках согласованной задачи означают создание или редактирование файлов непосредственно на GitHub.
- Готовые заметки и согласованные исправления сохранять в `v5`. Пользователь осведомлён, что это запускает публикацию сайта.
- Если пользователь просит черновик без публикации, использовать отдельную ветку и сообщить её имя.
- Выполнять задачу в согласованном объёме. Сопутствующие исправления ссылок и навигации допустимы, если необходимы для результата; не переписывать несвязанные заметки и общую карту библиотеки по собственной инициативе.
- Переименования сопровождать проверкой и исправлением входящих ссылок. Удаление заметок и крупную перестройку структуры предварительно согласовывать, если они ещё не поручены явно.
- Не менять настройки Quartz, тему, зависимости и сборку при обычной работе над содержанием.
- Не создавать конкурирующие копии спецификации и терминологии. При обнаружении содержательного противоречия явно сообщить о нём.

## Git и синхронизация

- Перед записью читать текущую версию файла и состояние ветки. Сохранять чужие изменения.
- Группировать логически связанные изменения в понятные коммиты, по возможности атомарно.
- Не использовать принудительную перезапись истории. Если ветка изменилась во время работы, перечитать изменения и согласовать с ними результат.
- Пользователь отправляет локальные изменения через Push перед нашей работой и получает изменения через Pull после неё. Не утверждать, что локальное хранилище синхронизировано, без подтверждения.

## Проверка и отчёт

- Проверять математическую согласованность, YAML, имена файлов, внутренние ссылки, пути к рисункам, разделители формул и размещение Mermaid.
- Навигационным заметкам задавать `order: 0`. Остальной порядок сохранять в соответствии с серией.
- Различать доказательство, вычисление для частного случая и гипотезу.
- После записи проверить сохранённое содержимое или diff коммита.
- В ответе кратко перечислить изменённые файлы и дать ссылку на коммит. Статус сборки сообщать только после проверки; не выдавать создание коммита за успешную публикацию.
- Источником правил оформления служит файл в `instructions`. Его дальнейшие изменения выполнять в репозитории, чтобы не поддерживать несколько расходящихся версий.
