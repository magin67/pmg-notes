# Инструкция по оформлению Markdown-заметок PMG

Эти правила следует применять при подготовке итоговых, теоретических и исследовательских заметок проекта в формате Markdown для Obsidian.

# 1. Общие замечания

Заметки создаются и редактируются непосредственно в `pmg-library` этого репозитория. Пользователь получает изменения в локальное хранилище Obsidian через Git Pull.

Не использовать оформление, специфичное для интерфейса ChatGPT, если оно не переносится непосредственно в Markdown.

## 1.1. Главное правило

Markdown-заметка должна одновременно быть:
- удобной для чтения и редактирования в Obsidian;
- математически точной;
- пригодной как исходный материал для последующего переноса в LaTeX-статью или монографию.

## 1.2. Именование заметок (файлов .md)

- В именах файлов использовать обычные пробелы, не заменять их дефисами.
- В имени файла избегать запрещённых Windows символов; например, двоеточие из `title` заменять на `-`.
- Названия в ссылках писать с пробелами.
- Не дублировать название файла заметки заголовком `#` в теле заметки.

## 1.3. Использование символов

- Избегать без особой необходимости использования символов, которых нет на стандартной клавиатуре.
- В частности избегать длинного тире `—`; при необходимости использовать `-`.

## 1.4. Для публичной библиотеки: Obsidian и Quartz

- Название страницы задавать в YAML-поле `title`.
- Начинать текст с вводного абзаца, разделы оформлять с `##`.
- Определения и результаты выделять цветными блоками callout, доказательства делать сворачиваемыми по правилам раздела 3.3. Диаграммы Mermaid размещать отдельно, вне callout.
- В Markdown-таблицах не оставлять неэкранированный разделитель `|` внутри ссылки с псевдонимом: он может создать лишнюю колонку. Предпочтительно вынести такую ссылку в соседний абзац, оставив в ячейке обычный текст. Проверять одинаковое число ячеек у заголовка и строк таблицы.

## 1.5. Изображения серии

- Все изображения серии хранить в её подпапке `images`; для русской и английской версий использовать подпапки соответствующих языковых серий.
- В заметках ссылаться на файл с учётом этой подпапки, например `![[images/Схема сочленения.svg]]`.
- При переносе изображения обновлять все ссылки на него и пути в программах построения и перевода рисунков. Программы должны сохранять новые изображения сразу в `images`.
- Названия и содержимое существующих изображений при одном лишь упорядочении папок сохранять.

# 2. Оформление формул

Использовать стандартный Markdown и LaTeX-совместимый синтаксис математических формул, поддерживаемый Obsidian.
## 2.1. Строчные формулы

Строчные математические выражения оформлять одиночными символами `$`.

Правильно:
```markdown
Дуальное представление гриниана обозначается $Q_1$, а остовное число — $\tau$.
```
Не использовать для строчных формул конструкции `\(...\)`.

## 2.2. Блочные формулы

Отдельные формулы оформлять двойными символами `$$`. Открывающий и закрывающий разделители должны занимать отдельные строки.

После программной вставки или замены текста проверять разделители в окончательном содержимом, отправляемом в репозиторий, и повторно в сохранённом файле на GitHub. Отдельно проверять формулы внутри callout. Одиночный `$` на отдельной строке недопустим; проверка промежуточной локальной копии не заменяет проверку сохранённой версии.

## 2.3. Пустые строки вокруг блочных формул

Для совместимости Obsidian, GitHub и Quartz обязательно оставлять пустую строку перед открывающим разделителем и после закрывающего.

Правильно:
```markdown
Из определения следует

$$
Q_1=\sum_{i<j}q_{ij}\{a_i,a_j\}
$$

После нормировки получаем

$$
Q_1=-\frac12\sum_{i<j}R_{ij}\{a_i,a_j\}
$$

Далее рассмотрим свойства формы.
```

Не использовать конструкции `\[...\]` и запись блочной формулы вместе с разделителями в одной строке.

## 2.4. Формулы не помещать в code block

Математические формулы должны оставаться обычными Markdown/LaTeX-формулами.

Code block использовать только тогда, когда необходимо показать исходный код, синтаксис Markdown, LaTeX или программный код как текст.

## 2.5. Выделение важных формул

Для ключевых определений и результатов допускается использовать
```latex
\boxed{...}
```
но не следует заключать в `\boxed` каждую формулу подряд.

`boxed` предпочтительно использовать для:
- основных определений;
- итоговых тождеств;
- доказанных или явно сформулированных рабочих формул;
- ключевых результатов раздела.

Промежуточные преобразования обычно оставлять без рамки.

## 2.6. Добавление тегов

Использовать `\tag{...}` выборочно: только для формул, на которые есть или предполагаются ссылки. Не нумеровать все формулы подряд.

## 2.7. Нотация

Сохранять обозначения, уже принятые в проекте.

В частности:
- единичная форма — $e$;
- лапласиан — $L$, гриниан — $\mathrm{Gr}$; матрицы — $\mathbf L$ и $\mathbf{Gr}=\mathbf L^+$; $\mathbf G$ сохраняется за грамианом;
- остовное число — $\tau$;
- дуальные грейд-полиформы в основной нормировке — $Q_k$, где $Q_0=e$;
- вспомогательная лесная нормировка — $\widetilde Q_k=\tau Q_k$ и $\widetilde D=\tau D$;
- дуальное представление гриниана — $Q_1$; при центрированном отождествлении $\mathcal C:a_i^\vee\mapsto p_i=a_i-h$ имеем $\mathcal C(Q_1)=\mathrm{Gr}$; когда оба пространства участвуют в одной формуле, $a_i^\vee$ обозначает дуальный элемент, $a_i$ - прямую вершину; в разделе об одной дуальной стороне знак $\vee$ можно опускать по явному соглашению;
- эффективные резистенсы — $R_{ij}$; суммы по вершинам — $R_i=\sum_jR_{ij}$;
- средние резистенсы — $\bar R_i=R_i/n$ и $\bar R=n^{-2}\sum_iR_i$, включая нулевую диагональ;
- каноническая симметричная векторная запись гриниана на дуальных аргументах — $Q_1=\sum_{i<j}\gamma_{ij}[a_{ij}]^2$, где $\gamma_{ij}=-\mathrm{Gr}_{ij}$;
- для расчёта экспоненты использовать векторные факторы и правила границ; полярные и разрезные записи сохранять как эквивалентные представления с явно указанным смыслом коэффициентов;
- полярная форма — $\{a,b\}$;
- квадратичная форма — $[X]^2$;
- вектор пары обозначать $a_{ij}=a_j-a_i=(a_i a_j)$; после определения использовать $a_{ij}$ и $[a_{ij}]^2$ без дополнительных круглых скобок;
- для границ более высокого грейда сохранять круглые скобки, например $(a_i a_j a_k)$; буквенная запись $(ab)$ также обозначает разность $b-a$;
- экспонента гриниана в дуальном представлении — $D=\exp Q_1$, $\mathcal C(D)=\exp(\mathrm{Gr})$; дуальность является взаимным отношением экспонент, а не собственным именем одной из них; прежние определения через $\operatorname{dex}$ не переносить в действующую серию;
- в симметричном случае лапласиан и гриниан являются векторными формами первого грейда; их экспоненты — граничными полиформами, высшие грейды которых состоят из форм на внешних произведениях векторов;
- матричное псевдообращение, внешнее удаление и обратимость экспоненты при произведении различать явно; после переноса в одно пространство $\exp L\,\exp(\mathrm{Gr})=\exp(L+\mathrm{Gr})$, а мультипликативная обратная равна $\exp(-L)$;
- обычная предельная форма обозначается $T_n$ или другим явно оговорённым обозначением и не должна смешиваться с обозначением дуального грейда.

В русских текстах использовать форму прилагательного «остовной»: «остовной лес», «остовной 2-лес», «остовной коэффициент». Форма среднего рода - «остовное дерево»; остальные формы согласуются по обычным правилам склонения. Вариант «остовный» не использовать.

При наличии неоднозначности между ранее использовавшимися обозначениями сначала уточнять терминологию, а не вводить новое обозначение незаметно.

### Читаемость индексов

В координатных и тензорных формулах использовать соглашение Эйнштейна: индекс, встречающийся в одном произведении дважды, один раз сверху и один раз снизу, подразумевает суммирование. Не добавлять к такой свёртке знак суммы: писать $d_i h^i$, $g_{ij}b^j$, $g^{ij}d_j$. Диапазон индексов задавать в тексте. Явные суммы сохранять при ограничении области (например, $i<j$), суммировании коэффициентов без парного индекса и в формулах, которые не являются такой тензорной свёрткой.

Избегать индексов внутри индексов. При фиксированном графе обозначать $M=\exp L$ и писать $u_M(f)$ вместо $u_{M_G}(f)$. При фиксированной метрике можно писать $u(f)$, явно оговорив это сокращение. Для выбранных пар удобны $t_\alpha,c_\alpha,R_\alpha$ вместо $a_{e_\alpha},c_{e_\alpha},R_{e_\alpha}$: значения сокращений задаются перед формулой. Если сравниваются разные метрики или графы, зависимость сохранять через явно названные $M,N$ либо аргументы функции.

### Запись произведений

- Между внешними объектами, в том числе границами, внешнее произведение подразумевается по умолчанию. Знак $\wedge$ опускать: писать $(ab)(cd)$ вместо $(ab)\wedge(cd)$, $uv$ вместо $u\wedge v$, $(B_1)\cdots(B_q)$ вместо $(B_1)\wedge\cdots\wedge(B_q)$.
- Произведение форм также записывать без знака: $[X]^2[Y]^2$. Его смысл определяется правилом умножения форм.
- Другой тип произведения указывать явно. В частности, скалярное произведение записывать как $X\cdot Y$ или $(ab)\cdot(cd)$; не заменять его записью без знака.
- Сохранять соглашение о норме $X^2=X\cdot X$: внешнее самопроизведение $X\wedge X$ не сокращать до $X^2$.
- Правило действует одинаково в русских и английских заметках, включая доказательства, таблицы и примеры.

### Объекты, элементы, точки и нормы

- Общий термин для внешней алгебры - «внешняя структура»; её грейд указан явно. Симплекс является простой структурой, а не произвольной суммой симплексов. Форму симплекса отличать от самого симплекса.
- Структуру первого грейда называем объектом. Объект аффинного веса $1$ - элемент, веса $0$ - вектор. Не повторять «единичного веса» после каждого употребления слова «элемент»; определить соглашение при первом введении.
- Точка, или локальный элемент, имеет вес $1$ и нулевую норму. Нелокальный элемент имеет ненулевую норму. Не называть произвольную аффинную комбинацию точек точкой: она является элементом, локальность требует отдельной проверки.
- «Вершина» и «узел» обозначают роль элемента в графе и не задают его норму. «Двуточечный вектор» использовать для разности точек; без условия локальности - «вектор пары вершин» или «разность элементов». Термин «двуэлементный вектор» не вводить.
- В симметричной изотропной модели центр элемента $s$ есть точка $s_0=\pi(s)=s-s^2z/2$. Различать элемент сферы $s=s_0+s^2z/2$, сферу как множество точек и её центр $s_0$. При положительной метрике перемещений $s^2>0$ даёт сферу, $s^2=0$ - точку, $s^2<0$ не даёт вещественных точек сферы. Норму произвольного элемента обозначать $s^2=s\cdot s$; обозначение $\rho(G)$ сохранять за резистивным радиусом графа.
- Нулевой вектор $0$, ненулевой изотропный вектор и выделенный нуль-вектор $z$ различаются. Последний задаёт аффинный вес $\varepsilon(U)=U\cdot z$; одной нулевой нормы для его определения недостаточно. При произвольном весе использовать «изотропный объект».
- Норма объекта означает квадратичную величину $X^2=X\cdot X$. При $X^2\ge0$ корень $\|X\|=\sqrt{X^2}$ называется линейной нормой. В неопределённой метрике норма может быть отрицательной. Не заменять её термином «метрический квадрат». Не называть $X\cdot X$ «квадратом нормы» без уточнения, что речь о линейной норме. В резистивной метрике допустимо название «резистивная норма».
- Различать структуру $X$, форму $[X]^2$ и численную норму $X^2$. Норма формы определяется нормированным потенциалом. Для $[X]^2$ она совпадает с нормой аргумента в области действия метрического тождества.
- В EN использовать object, element, affine vector, point / local element, nonlocal element, center of an element, sphere element, isotropic object / vector, distinguished null vector. Для нормы - quadratic norm / resistance norm, linear norm. Обычные выражения «элемент матрицы» / matrix element не подчиняются специальному определению элемента веса $1$.

### Радиус и диаметр описанной сферы

- Резистивный радиус графа обозначается $\rho=R_{\mathrm{sph}}^2$, резистивный диаметр - $D_{\mathrm{res}}=4\rho=(2R_{\mathrm{sph}})^2$. Оба параметра квадратичны; линейные радиус и диаметр равны $R_{\mathrm{sph}}$ и $2R_{\mathrm{sph}}$.
- Прежнее название «метрическая масса» не использовать как действующий термин. При чтении старых материалов проверять нормировку; замена названия не должна незаметно менять значение параметра. В английском тексте использовать resistance radius и resistance diameter с явным определением; не отождествлять последний с максимальным попарным резистенсом.

### Обозначения матричного и полиформенного представлений

Один и тот же математический объект может использоваться в разных представлениях, например как матрица и как полиформа.

Если из контекста представление однозначно, используется обычное обозначение объекта: $L, R$ и т. д.

Если два представления одного объекта встречаются одновременно, простое обозначение сохраняется за полиформой, а матричное представление выделяется полужирным начертанием:

$L$ — полиформа лапласиана,  
$\mathbf L$ — матрица лапласиана.

Аналогично: $R$ и $\mathbf R$.

Полужирное начертание относится к матрице как объекту. Её скалярные элементы писать обычным начертанием: $L_{ij}$, $R_{ij}$; например, $L=\sum_{i,j}L_{ij}[a_i,a_j]$. Для подматрицы, которая сама является матрицей, полужирное начертание сохраняется: $\mathbf L_{\widehat r,\widehat r}$.

Для обозначения точки не использовать латинскую букву $o$: она визуально похожа на ноль. Обычно использовать $p$; если $p$ уже занят, выбрать другую свободную букву, например $h$, и явно определить её смысл.

Не следует вводить специальные индексы или декоративные начертания только для указания типа представления, если это можно выразить контекстом или типографикой. Индексы сохраняются для математического содержания: грейда, типа, номера компоненты и т. п.

### Грамианы, матрица Грина и би-координаты

- Грамиан выбранных элементов обозначать $G$ или $\mathbf G$, его элементы - $g_{ij}=a_i\cdot a_j$. При нескольких наборах указывать аргументы или содержательный индекс, например $G(u_1,\ldots,u_k)$ или $\mathbf G_u$ для грамиана разностей. Не переобозначать грамиан ради освобождения буквы для матрицы Грина.
- Матрицу Грина обозначать $\mathrm{Gr}=L^+$; при полужирном обозначении матриц - $\mathbf{Gr}=\mathbf L^+$. Это один объект: $L^+$ подчёркивает псевдообращение, $\mathrm{Gr}$ служит его именем. Матрица Грина является грамианом векторов от вершин к центроиду; она отличается от грамиана самих локальных вершин.
- Для локальных вершин $\mathbf G=-\mathbf R/2$. Грамиан расширенного набора $(a_1,\ldots,a_n,z)$ обозначать $\mathbf G_z$; индекс $z$ означает добавленные строку и столбец нуль-вектора. Не смешивать $\mathbf G$, $\mathbf G_z$ и $\mathbf{Gr}$.
- Обозначение $\mathbf B$ использовать для матриц би-координат, в частности матриц влияния. Оно не обозначает грамиан. Матрица инцидентности также является матрицей координат векторов рёбер; при использовании $B$ этот смысл нужно указать.
- Эти соглашения действуют одинаково в русских и английских заметках. Граф $G$, в отличие от матрицы $\mathbf G$, сохраняет своё обозначение.

## 2.8. Независимые проверки

Если формула была специально проверена независимым способом, это следует сохранять в итоговой заметке.

Особенно важно отличать:
- вычисление, использующее предполагаемую общую формулу;
- независимое вычисление непосредственно из определения.

Это необходимо для контроля возможных круговых доказательств.

## 2.9. Точки после формул

В конце блочных формул, особенно формул с `\tag{...}`, не ставить знаки препинания. Пунктуацию переносить в окружающий текст, чтобы она не воспринималась как часть математической записи.

## 2.10. Перенос длинных формул
Если одна формула переносится на следующую строку, перенос выполнять по знаку операции или отношения: $=, +, -, \cdot, \times$ и т. п. Знак оставлять в конце предыдущей строки и повторять в начале следующей.  
Это правило относится именно к переносу одного выражения. В многострочной цепочке преобразований, где каждая строка представляет отдельный шаг вычисления, знак в конце предыдущей строки не дублировать.

## 2.11. Подготовка к будущему переносу в LaTeX

Формулы желательно писать сразу в синтаксисе, который без существенных изменений переносится в LaTeX.

Не использовать нестандартные Obsidian-конструкции внутри математических выражений, если без них можно обойтись.

Ключевые формулы и утверждения в дальнейшем могут получить семантические LaTeX-метки вида:
```latex
\label{eq:q1-forest}
\label{eq:cutexp}
\label{thm:dual-grades}
```
Поэтому при подготовке заметок желательно сохранять устойчивые названия основных формул и результатов.


# 3. Общая структура
## 3.1. Различать доказанные результаты и рабочие гипотезы

В исследовательских заметках обязательно явно отмечать статус утверждений.

Использовать формулировки:

- **доказано** — если имеется общее доказательство;
- **непосредственно вычислено** — если результат получен для конкретного случая;
- **проверено на примерах** — если имеются несколько независимых проверок;
- **рабочая гипотеза** — если общий результат предполагается, но ещё не доказан;
- **предположительно** — для интерпретаций, требующих дальнейшего исследования.

Не превращать наблюдаемую закономерность в теорему без отдельного доказательства.

## 3.2. Разделы заметки

Для крупных итоговых заметок предпочтительна структура:
```markdown
Вводный абзац.

## Исходная постановка

## Определения

## Основные результаты

## Доказательство или вывод

## Примеры

## Интерпретация

## Статус результата

## Открытые вопросы

## Итог
```
Конкретные разделы могут меняться в зависимости от темы.

Не следует искусственно создавать разделы, если материала для них нет.

## 3.2. Заголовки и нумерация

В исследовательских Markdown-заметках ручная нумерация разделов допустима, но не обязательна.

Если заметка в дальнейшем предназначается для переноса в статью или монографию, предпочтительно не строить существенные ссылки вида «см. раздел 7» вручную.

Лучше ссылаться по названию раздела или по имени Obsidian-заметки.

Окончательную автоматическую нумерацию разделов, формул, теорем, рисунков и таблиц предполагается выполнять позднее средствами LaTeX.

## 3.3. Цветные блоки и сворачиваемые доказательства

В русских и английских математических заметках использовать одинаковую визуальную структуру: определения и результаты видны сразу, доказательства читатель раскрывает отдельно.

- **Определения, леммы, утверждения, теоремы и следствия** помещать в открытый цветной блок `> [!info] Краткое название`. Внутри сохранять метку **Определение.**, **Лемма.**, **Утверждение.**, **Теорема.** или **Следствие.**; при необходимости ссылок добавлять номер. Для краткого напоминания определения достаточно содержательного заголовка блока.
- **Доказательство** помещать в отдельный блок `> [!note]- Доказательство` сразу после формулировки и относящейся к ней атрибуции. Знак `-` после `[!note]` означает, что блок изначально свёрнут. При нескольких результатах уточнять заголовок: `Доказательство леммы 2`. Сам текст начинать с **Доказательство.**, завершать символом `$\square$`. Обоснование или вывод оформлять так же, с соответствующим заголовком.
- **Примеры** при необходимости выделять открытым блоком `> [!example] Название примера`; дополнительные подробности вычисления можно свернуть в `> [!example]- Подробности вычисления`. Не помещать целый большой раздел с рисунками и таблицами в один блок: достаточно выделить его основной результат.
- **Замечания, ограничения и происхождение результата** при необходимости выделять открытым `> [!note] Краткое название`. Условия применимости, сама формулировка, основные формулы результата и сведения об источнике должны оставаться видимыми вне свёрнутого доказательства.
- Названия блоков переводить вместе с текстом заметки: например, `Definition`, `Lemma`, `Proof`. Служебные типы `info`, `note`, `example` не переводить. Цвет задаёт тема Obsidian или Quartz; не задавать его вручную через HTML и не полагаться только на цвет без текстовой метки.
- Номера утверждений и формул вести независимо. Не заменять цветной блок одной жирной меткой; вместе с тем обычные связующие абзацы оставлять вне блоков, чтобы выделение сохраняло смысл.

**Синтаксис.** Каждая строка внутри callout, включая пустые строки и строки формул, начинается с `>`. Между соседними блоками оставлять пустую строку без `>`. Вокруг блочной формулы внутри callout ставить пустые строки `>`; открывающий и закрывающий разделители записывать отдельными строками `> $$`. Не вкладывать доказательство в блок формулировки и не вкладывать callout друг в друга. Рисунки, подписи и Mermaid оставлять вне блоков.

Пример разметки:

```markdown
> [!info] Положительность остовного числа
> **Лемма.** Если конечный граф связен и проводимости его рёбер положительны, то
>
> $$
> \tau(G)>0
> $$

> [!note]- Доказательство
> **Доказательство.** Связный граф имеет остовное дерево. Вес каждого дерева положителен, поэтому положительна и сумма этих весов. $\square$
```

Образцы принятого оформления: определения в заметке [«Лапласиан - граф, электрическая сеть и квадратичная форма»](../pmg-library/ru/%D0%9D%D0%B0%D1%87%D0%B0%D0%BB%D0%BE%20%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D1%8B%20%D0%B8%20%D0%BE%D1%81%D0%BD%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/%D0%92%D0%B2%D0%B5%D0%B4%D0%B5%D0%BD%D0%B8%D0%B5/%D0%9B%D0%B0%D0%BF%D0%BB%D0%B0%D1%81%D0%B8%D0%B0%D0%BD%20-%20%D0%B3%D1%80%D0%B0%D1%84,%20%D1%8D%D0%BB%D0%B5%D0%BA%D1%82%D1%80%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B0%D1%8F%20%D1%81%D0%B5%D1%82%D1%8C%20%D0%B8%20%D0%BA%D0%B2%D0%B0%D0%B4%D1%80%D0%B0%D1%82%D0%B8%D1%87%D0%BD%D0%B0%D1%8F%20%D1%84%D0%BE%D1%80%D0%BC%D0%B0.md) и лемма со сворачиваемым доказательством в [«Вариации одной связи»](../pmg-library/ru/%D0%9D%D0%B0%D1%87%D0%B0%D0%BB%D0%BE%20%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D1%8B%20%D0%B8%20%D0%BE%D1%81%D0%BD%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F/%D0%92%D0%B2%D0%B5%D0%B4%D0%B5%D0%BD%D0%B8%D0%B5/%D0%92%D0%B0%D1%80%D0%B8%D0%B0%D1%86%D0%B8%D1%8F%20%D0%BE%D0%B4%D0%BD%D0%BE%D0%B9%20%D1%81%D0%B2%D1%8F%D0%B7%D0%B8.md).

При проверке страницы убедиться, что формулировка видна сразу, доказательство изначально свёрнуто, раскрывается нажатием на заголовок и правильно отображает формулы, списки и ссылки. Проверить длинные формулы с учётом более узкой области внутри блока.

## 3.4. Сплошная черта

Не использовать сплошную черту "---", если после нее идет следующий раздел.
Разделение чертой допускается только внутри одного раздела, чтобы выделить тематически разные части раздела.

## 3.5. Ссылки между заметками

Читатель может открыть любую заметку отдельно и не знать порядка серии. Поэтому каждая отсылка к другой заметке должна содержать явную Obsidian-ссылку на её название или нужный раздел. Текст ссылки должен называть заметку либо содержательно описывать её тему.

В заголовках, основном тексте, подписях к рисункам, навигаторах и истории редакций публичных заметок не использовать внутренние коды серий. Называть серию по содержанию, а при обращении к результату давать ссылку на конкретную заметку или раздел и пояснять, какой закон, определение или вывод используется. Правило действует в русских и английских текстах. Коды допускаются в рабочей карте проекта и служебных материалах, где они являются явно определёнными идентификаторами планирования; читателю математической заметки не должно требоваться знание этих кодов.

Не использовать вместо такой ссылки выражения «в первой заметке», «во второй заметке», «в предыдущей заметке», «в следующей заметке», «в последней заметке» и аналогичные указания на положение в серии. Наличие порядка чтения в навигаторе или YAML-поля `order` этого требования не отменяет. Правило действует в русских и английских текстах.

Если нужная заметка ещё не создана, сформулировать тему продолжения без ссылки на несуществующий файл. После её создания добавить явную ссылку.

Для навигационной заметки, имя которой совпадает с именем её папки, использовать полный путь внутри pmg-library и сохранять короткое видимое название через псевдоним. Например: [[ru/Резистивная геометрия и дуальность/Гриниан и дуальность полиформ/Гриниан и дуальность полиформ|Гриниан и дуальность полиформ]]. Короткая ссылка только по имени может не разрешиться после преобразования такой заметки в страницу папки. В таблицах разделитель псевдонима экранировать или вынести ссылку из таблицы; проверять адрес в готовой HTML-сборке.

Если известное понятие уже подробно разобрано в отдельной заметке, предпочтительно дать Obsidian-ссылку:
```markdown
[[Каноническое векторное представление гриниана]]
```
вместо полного повторения материала.

Однако заметка должна сохранять достаточную самостоятельность: необходимые для понимания определения и основные формулы следует кратко повторять.

## 3.6. Избегать лишнего дублирования

При подготовке серии итоговых заметок одна и та же тема не должна подробно пересказываться в каждой из них.

Например:
- взаимная дуальность экспонент лапласиана и гриниана — в основной заметке;
- внешняя экспонента и представления гриниана — в одноимённой заметке;
- каноническое векторное представление $Q_1$, центроидные коэффициенты и знаковые остовные суммы — в заметке «Каноническое векторное представление гриниана»;
- конкретные графы — в каталоге типовых графов;
- тождества разрезов — в отдельной заметке о разрезных формах.

В других заметках достаточно краткой ссылки и необходимых формул.

## 3.7. Стиль математического текста

Сначала назвать вопрос, который решает вводимый объект, затем дать определение и объяснить смысл формулы. Новые понятия и обозначения определять до использования. Существенные переходы пояснять промежуточным шагом или небольшим разобранным примером.

Основная идея должна быть понятна без раскрытия доказательств. В свёрнутом блоке оставлять подробный вывод, а необходимое объяснение - в основном тексте. Сложность обозначений уменьшать явными локальными сокращениями; не заменять рассуждение словами «очевидно» и «непосредственно».

Предпочитать простые фразы. Избегать лишних личных оборотов «мы», «нас», «нам», «наш»; использовать безличное изложение или краткие формулировки «Рассмотрим», «Определим». Не вводить термин ради единственного употребления и не расширять понятную заметку повторениями. Условия применимости и различия формы, объекта и численной оценки сохранять явно. Электрическая сеть является одной из интерпретаций графа; общую геометрическую постановку не формулировать исключительно через токи и проводимости.

## 3.8. Источники публичных заметок

- В русских и английских публичных заметках ссылаться на доступную читателю внешнюю литературу и опубликованные заметки библиотеки.
- Не включать в библиографию ссылки на исследовательские заметки внутренней библиотеки, недоступные внешнему читателю. Не отсылать к ним за определениями, доказательствами или пояснениями.
- Если нужно отметить происхождение материала, достаточно фразы «Заметка основана на исследованиях автора в рамках PMG» без ссылки на внутренние файлы.
- Необходимое обоснование приводить в публичном тексте либо давать точную ссылку на доступный источник. Если доказательства нет, явно указывать статус результата.
- Это правило относится к публичному изложению; при подготовке заметки внутренние исследовательские материалы следует изучать и проверять.

## 3.9. Происхождение результатов и научная новизна

- Различать математический статус (определение, доказанный результат, гипотеза) и происхождение результата. Наличие доказательства в заметке не означает научной новизны.
- У существенного заимствованного результата указывать автора и точное место в источнике рядом с формулировкой, а не только в заключительной библиографии.
- Если известная конструкция записана в обозначениях PMG, с весами или производящей переменной, явно назвать это изложением или адаптацией известной конструкции.
- Для выводов из известных результатов указывать исходные теоремы и собственный переход между ними. Пометка «вывод в этой заметке» не означает «впервые в литературе».
- Интерпретации в языке PMG, выбранные нормировки, примеры и вычислительные проверки обозначать по их фактической роли; не выдавать их автоматически за новые математические результаты.
- Если предполагается научная новизна, отдельно сформулировать, что именно претендует на новизну, с какими работами выполнено сравнение и проверен ли приоритет. Отсутствие найденной ссылки не доказывает отсутствия результата у других авторов.
- В итоговом навигаторе исследовательской серии сводить существенные результаты в карту «результат - источник или вывод - роль в PMG - статус притязания на новизну». Эта карта дополняет локальную атрибуцию в самих заметках.

# 4. Навигация и рисунки публичной библиотеки

- Навигационным заметкам задавать YAML-свойство `order: 0`. Порядок содержательных заметок согласовывать с текущей серией.
- Сохранять существующие YAML-поля и принятый формат дат и ревизий. Не добавлять произвольную новую схему метаданных.
- В Mermaid вершины графов изображать кругами. Диаграммы размещать вне callout.
- SVG и другие рисунки хранить в принятой в соответствующем разделе папке; проверять ссылки из заметок.
- При создании перевода сохранять математическое содержание, обозначения и согласованность ссылок между языковыми версиями.
- Актуальные спецификация и терминология в `pmg-library/ru/Начало работы и основания/Основания` определяют математические обозначения; примеры в этой инструкции не заменяют спецификацию.

## 4.1. Тематическая классификация серий

- Читательская структура задана в `pmg-library/ru/Навигация/Тематический указатель.md` и `pmg-library/en/Navigation/Thematic Index.md`: пять тематических разделов и отдельный вход «Начало работы и основания». На верхнем уровне `ru` и `en` им соответствуют папки разделов; папка каждой серии находится внутри её основного раздела. Программные примеры сохраняют отдельный вход `PythonExamples`.
- У серии одно основное место, выбранное по её главному вопросу. В навигаторе можно указать до двух дополнительных тематических входов с пояснением связи; на странице соответствующего раздела добавить обратную ссылку. Дополнительные входы оформляются ссылками и не создают копий серии.
- Страница раздела лежит в его папке и имеет то же имя, чтобы служить оглавлением папки в Quartz. При переносе серии переносить вместе с ней рисунки и данные, обновлять внутренние ссылки, служебные инструкции и пути в проверочных скриптах. Старые адреса страниц сохранять через YAML-поле `aliases` и проверять перенаправления в собранном сайте.
- Навигатору серии задавать два-четыре YAML-тега из раздела «Поиск по тегам» / «Search by tags» тематического указателя. Для переводов использовать соответствующие пары словаря. Тег относится к содержанию серии и не означает, что тема присутствует в каждой заметке.
- Тематическую принадлежность, обязательные предпосылки и исследовательские продолжения различать явно. Неподготовленную серию описывать как планируемую, без ссылки на несуществующую страницу.
- При добавлении серии согласовывать оба тематических указателя, страницы её основного и дополнительных разделов, языковые главные страницы и рабочую карту. Содержательные заметки считать отдельно от навигаторов, тематических страниц, справочников и программных примеров. Исследовательские коды карты сохраняют самостоятельное значение и не задают читательскую классификацию.

### Теги и общий раздел навигации

- В «Навигации» / Navigation находятся тематический указатель со словарём тегов и карта библиотеки. Русская и английская карты согласуются по направлениям, опубликованным результатам и открытым вопросам. Состав серий приводится в тематическом указателе. Карта описывает актуальное состояние; хронология выпусков и редакционных проверок сохраняется в истории Git.
- Выбирать теги по содержанию серии. Использовать парные написания из словаря без дополнительных синонимов. Общие слова «графы», «полиформы» и «математика» не использовать как теги, поскольку они почти не различают материалы библиотеки. Само использование определителя не задаёт тематическую принадлежность серии.
- Тег «восстановление» / reconstruction включает ограничения и контрпримеры. Теги не задают предварительное чтение и состояние подготовки серии.

## 4.2. Порядок папок на сайте

- `order: 0` сохраняет положение навигатора внутри папки. Для порядка самой папки среди соседних папок использовать отдельное числовое поле `folder_order` в её странице-оглавлении. Quartz применяет его в дереве Explorer и списках папок; это поле само по себе не настраивает Obsidian.
- Верхний уровень RU и EN: 10 — начало работы и основания; 20 — алгебра и комбинаторика полиформ; 30 — резистивная геометрия и дуальность; 40 — инварианты, разложения и спектры; 50 — преобразования и сочленения графов; 60 — направленные графы и расширения; 70 — программные примеры; 80 — навигация. Это порядок навигации, не обязательный маршрут чтения.
- Значения у языковых пар должны совпадать. Папки без `folder_order` следуют после упорядоченных папок по алфавиту. Для заметок продолжает действовать `order`.


# 5. Самодостаточность и проверяемость материала

1. **Предпосылки.** У существенных утверждений явно указывать условия применимости. Общие условия можно задать для раздела целиком, не повторяя их перед каждой формулой.
2. **Статус.** Различать определения, доказанные результаты, гипотезы и вычислительные наблюдения. Если доказательство находится в другом месте, давать ссылку.
3. **Адресуемость.** Основные результаты размещать в разделах с содержательными, по возможности устойчивыми заголовками. Идентификаторы и номера добавлять там, где нужны точные ссылки.
4. **Смысловые связи.** Ссылаться на необходимые определения, доказательства и связанные результаты, поясняя назначение ссылки, когда оно неочевидно.
5. **Рисунки.** Сопровождать содержательные рисунки текстом, позволяющим понять изображённый объект и основной вывод без просмотра изображения. Полностью дублировать рисунок словами не требуется.



## Программные примеры

- В примерах кода обозначать вершины буквами `a, b, c, ...`, а не числами. Числа оставлять для коэффициентов, грейдов и индексов массивов. Сначала создавать элементы, затем формы и лапласианы; имена вершин в тексте, коде и рисунках должны совпадать.
- Для демонстрации алгебры выводить сами формы и полиформы, в том числе экспоненту с группировкой по грейдам. Численные оценки через потенциалы и нормы показывать отдельным шагом.
- Кодовые заметки называть с префиксом «Пример:» / «Example:», без окончания «на Python» / «in Python». В имени файла двоеточие заменять на « - ». При переименовании сохранять старые адреса через aliases и обновлять входящие ссылки.


## Обновление карты библиотеки

- Сохранять коды направлений и согласовывать обе языковые версии. Проверять статусы по опубликованным заметкам и навигаторам.
- Новые открытые вопросы связывать с исходной заметкой и формулировать оставшуюся задачу. После её раскрытия обновлять запись и ссылку на результат.
- При изменении карты обновлять `updated` и `revision`. Хронологию выпусков, старые очереди работ и отчёты о проверках в текст карты не добавлять.
